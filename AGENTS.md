# HandUp — Agent Rules

## 0. Start here (every task)

1. Read the GitHub issue you are implementing, then its user story in `docs/PRD.md` §5 and the product rules it
   cites (§4.x). For UI work also read `docs/ui-spec.md`. Restate the acceptance criteria (AC) as a checklist
   before writing code. No GitHub access? The issue's AC are the matching story's AC in `docs/PRD.md` §5.
2. **Scope = every AC of the issue.** "Implement #6" is a pointer to the issue, not a smaller scope. Never drop
   an AC silently. If one is truly blocked, say so in your plan *before* writing code and wait for an answer.
3. Work on exactly one issue per branch. Do not add features, screens or fields the issue does not ask for.
4. Follow TDD (§3.4): write failing tests first, show their failing output, then implement.
5. Missing infrastructure is not a reason to skip a layer. No database running? Still write the service and its
   `*.int.test.ts`, commit them, and report them as "written, not run" with the command to run them.
6. If the request conflicts with this file, the PRD or `prisma/schema.prisma`, stop and ask. Do not guess.
7. Finish with the Definition of Done (§7) and summarize: files changed, tests added, commands run with results,
   and every AC as `[x]` or `[ ]` with the reason.

## 1. Project context

<!-- Why: without this, agents assume a generic chat app and miss the visibility rules (hidden, anonymous) that
     make HandUp safe to use. -->

HandUp is live, anonymous Q&A and polling for lectures and talks of 20–200 people. Three roles —
**Host**, **Moderator** (both have accounts) and **Guest** (audience, no account, joins with a 6-character code) —
plus real-time question ranking, live polls, a session report and a documented **public REST API**.

second server.

### 1.2 Version traps — your training data is probably older than this stack

- **Next 16:** route protection lives in `src/proxy.ts` exporting `proxy()` (not `middleware.ts`).
  `cookies()`, `headers()`, `params` and `searchParams` are async — always `await` them.
- **Cache Components is on.** Never export `dynamic`, `revalidate` or `fetchCache` from a route (build error).
  A Server Component that reads cookies, headers or the database renders inside `<Suspense>` with a skeleton
  fallback. `new Date()` / `Date.now()` in a Server Component must come after `await connection()` inside that
  Suspense boundary — or pass `now` in from a Client Component.
- **Prisma 7:** import the client from `@/generated/prisma/client`, never from `@prisma/client`. Use the shared
  `db` from `@/lib/server/db`. The database URL lives in `prisma.config.ts`, not in the schema.
- **Tailwind 4:** design tokens are CSS variables in `src/app/globals.css` (`@theme`). There is no config file.
- **zod 4:** use `z.email()`, `z.url()`, `z.iso.datetime()`; custom messages use `{ error: "..." }`.

### 1.3 Architecture

```
src/
  app/
    (auth)/login, register     Host/moderator accounts
    dashboard/                 Sessions I host or moderate
    host/[code]/               Host + moderator console (guarded), report/
    join/[code]/               Guest board: ask, vote, polls
    settings/api-keys/         Public API keys
    api/v1/                    REST route handlers (thin); api/v1/public/** uses X-API-Key
    api-docs/                  Swagger UI page
  components/
    ui/                        Primitives: Button, Card, Tag, Dialog, EmptyState, Skeleton
    <feature>/                 questions/, polls/, sessions/, report/, moderation/
  lib/
    domain/                    PURE logic: join-code, rank-questions, merge-votes, poll-results, report. No I/O.
    server/                    `import "server-only"`: db.ts, auth/, services/, realtime.ts
    validation/                zod schemas shared by route handlers, Server Actions and forms
    api/                       http.ts — ok(), errorResponse(), ApiError, parseOrThrow(), toErrorResponse()
    client/                    Browser-only helpers (`use-session-events` SSE hook, `api-fetch`)
  generated/prisma/            Generated client (git-ignored, never edit)
  proxy.ts                     Redirects logged-out users away from guarded pages
prisma/                        schema.prisma, migrations/
tests/integration/             *.int.test.ts against real Postgres
e2e/                           Playwright specs
docs/                          PRD.md, ui-spec.md, architecture.md, database.md, standups/, retros/
```

Request flow — every feature follows it:

```
Page / Client Component ──► Server Action (app/**/actions.ts) ─┐
API client / guest board ─► Route handler (app/api/v1/**)  ────┼─► service (lib/server/services/*-service.ts)
                                                                │        ├─► domain functions (lib/domain, pure)
                                                                │        └─► db (Prisma) ──► Postgres
SSE   ◄── realtime.ts ◄────────────────────────────────────────┘   (services bump Session.version in the write transaction)
```

- **Route handlers and Server Actions are thin:** authenticate → `parseOrThrow(schema, input)` → call one service →
  return `ok(data)`; wrap the body in `try/catch` and return `toErrorResponse(err)`.
- **Only services import `db`.** Services enforce authorization themselves with `requireHost(sessionId, userId)`,
  `requireStaff(...)` (host or moderator) and `requireGuest(token, sessionId)`; `proxy.ts` only redirects.
- **Visibility is enforced in services, not in components.** Guest-facing DTOs never contain hidden questions,
  `MERGED` questions, or the author name of an anonymous question (PRD §4.2–4.3). Build them with one function
  per audience (`toGuestQuestion`, `toStaffQuestion`) and test both.
- **Domain functions are pure:** no imports from `next`, `react`, Prisma or `@/lib/server`. They are the most
  heavily tested code. Randomness is passed in (`generateJoinCode(random: () => number)`).
- **Time is always passed in.** `now: Date` is a *required* parameter — never a default such as
  `now = new Date()`. Read the clock once per request in the service and pass `now` down.
- **Server Components by default.** Add `"use client"` only to the smallest interactive leaf.
- **Real-time (PRD §4.7):** every service write that changes what someone sees calls
  `bumpSessionVersion(tx, sessionId)` inside the same `db.$transaction`. The SSE route only sends `{ version }`;
  clients refetch. Never put question text, names or vote data in an event.

| Thing | Convention | Example |
| --- | --- | --- |
| Files and folders | kebab-case — **also for component files** | `question-card.tsx` (not `QuestionCard.tsx`) |
| Next special files | As Next requires | `page.tsx`, `route.ts`, `actions.ts` |
| React components | PascalCase name, **named** export, one per file | `export function QuestionCard()` |
| Props and DTO types | `type` alias, not `interface`; props end in `Props` | `type QuestionCardProps = { … }` |
| Services | `<noun>-service.ts`, verb-first functions | `askQuestion({ guestId, body, now })` |
| Functions, variables | camelCase; booleans start with is/has/can | `rankQuestions`, `isPinned` |
| Constants | SCREAMING_SNAKE_CASE | `MAX_QUESTIONS_PER_MINUTE = 5` |
| Time fields | `*At`, stored UTC | `answeredAt` |
| zod schemas + types | `xxxSchema` and `type Xxx = z.infer<typeof xxxSchema>` | `askQuestionSchema` |
| API paths | `/api/v1/<plural-noun>`, JSON keys camelCase | `/api/v1/sessions/K7Q2XM/questions` |

No default exports except Next special files. No `I` prefix on types. No abbreviations beyond `id`, `url`, `db`.

### 1.5 Coding standards

- TypeScript strict: no `any` (use `unknown` + narrowing), no `!` non-null assertions outside tests, no `@ts-ignore`.
- Validate every external input with zod at the boundary: request bodies, query strings, params, form data, env.
- Text limits come from PRD §4 (question 3–300, display name ≤ 40, title 3–80, poll option ≤ 80).
- Writes that touch several rows (merge, pin, poll launch) run in `db.$transaction`.
- **Check-then-write is a race.** Two requests can both pass a `findUnique` or `count` before either one writes.
  Let the database decide:
  - Uniqueness (email, join code, one vote): insert and catch Prisma `P2002` with `isUniqueViolation()`
    (`src/lib/server/prisma-errors.ts`), or use `createMany({ skipDuplicates: true })`. Never `findUnique` then
    `create` (#40, #42, #43).
  - Limits and "only one" rules (5 questions per minute, one pinned question, one open poll): first take the lock
    that owns the rule (`SELECT … FOR UPDATE` on the Guest row; `lockSessionForStaffWrite()` for per-session
    rules), then count and write in the same transaction (#44, #59).
  - Lock order: question rows before the Session row. Votes lock the question and then bump `Session.version`,
    so never update the Session row first in a transaction that later touches questions; it deadlocks (#59).
- Keep functions under ~40 lines and files under ~200 lines; split by responsibility.
- Comments explain *why*. Link non-obvious decisions to their issue: `// Ties go to the older question (#6).`
- Every TODO has an issue: `// TODO(#12): paginate`. No orphan TODOs.

### 1.6 Testing strategy

<!-- Why: the P2 rubric grades TDD visible in git history, plus unit + integration + E2E. These rules make the
     agent produce exactly that evidence. -->

| Level | Tool | What | Where |
| --- | --- | --- | --- |
| Unit | Vitest + jsdom + Testing Library | Every domain function; components' visible behavior | Beside the file |
| Integration | Vitest (node) + real Postgres | Services and route handlers through Prisma, incl. 401/403/404 | `tests/integration/` |
| E2E | Playwright (desktop + Pixel 7) | One happy path per user story; real time with **two browser contexts** | `e2e/` |

- **One test per AC checkbox at minimum,** named after it:
  `it("puts the pinned question first even when it has fewer votes")`.
- One test file per source file, same base name, beside it. No catch-all test files.
- Vitest globals are off, so `vitest.setup.ts` calls Testing Library's `cleanup()` after each test.
- Cover the PRD boundaries: question of exactly 3 and 300 characters (and 2 / 301), the 5th vs 6th question in
  60 s, vote ties, merge when a guest voted both questions, poll with 0 responses, percentages that must add to 100.
- Use fixed dates (`new Date("2026-11-12T15:00:00Z")`) and seeded randomness in unit tests. Only exception: an
  integration test that calls a route handler (which owns `now`) may seed data relative to `Date.now()`, at least
  1 hour away from any boundary (e.g. the 60-second rate-limit window: seed 2 h ago or 1 s ago, never 59 s).
- Every visibility rule has a test from the guest side **and** the staff side.
- Query the DOM by role and label; no `data-testid` unless nothing else works. Use `@testing-library/user-event`.
- Integration tests use a real database (`docker compose up -d db`) and clean their tables in `beforeEach`.
  Do not mock Prisma or `@/lib/server/db`. Nothing external needs mocking: assert that `Session.version`
  increased after a write that others must see. Use `tests/integration/helpers.ts` (`resetDb`, factories).
- E2E real-time tests: open `browser.newContext()` twice (host + guest, or two guests), act in one, `expect` in the
  other with the default timeout — never `waitForTimeout`.
- **Before acting in another context, wait for server-confirmed state, not optimistic UI.** A vote button flips
  instantly; wait until the *other* screen shows the new count (it arrived over SSE) before e.g. merging.
- Locate inputs with `getByLabel("…", { exact: true })` when a button's accessible name contains the same words
  (the vote button "Your question, 0 votes" also matched the textarea "Your question").
- Integration factories sign tokens with the real clock (`new Date()`): route handlers verify with the real clock,
  so tokens signed at `TEST_NOW` would expire and break CI days later.
- Two writes that touch the same question row (vote and merge) lock it first with `lockQuestions(tx, ids)` and
  re-read inside the transaction. Add a concurrent `Promise.all` regression test for any new write of this kind.
- Every write covered by the check-then-write rule (§1.5) gets a concurrent test: `Promise.all` of 2–8 identical
  requests, committed red against the racy version first. Assert status codes **and** row counts
  (e.g. `[201, 409]` and one user), never just "no error".
- Don't time requests to test timing-sensitive code (flaky in CI); spy on the expensive call instead, e.g. bcrypt
  must run for an unknown email at login (#42).
- Coverage: ≥ 80% lines, branches and functions on `src/lib/domain` (enforced in `vitest.config.mts`).
- Commands: `npm test` (unit) · `npm run test:int` · `npm run test:e2e` · `npm run test:coverage`.

## 3. Scrum and Git workflow

### 3.1 Board

GitHub Project columns: **Backlog → Sprint Todo → In Progress → In Review → Done**. Milestones `Sprint 1`
(Nov 10 – Nov 11) and `Sprint 2` (Nov 12 – Nov 13). Due date Nov 13. Moving a card is the human's job; the agent mentions which
move is due.

### 3.2 Branches

`<type>/<issue-number>-<short-kebab-summary>` from an up-to-date `main`.
Types: `feature`, `fix`, `chore`, `docs`, `test`, `refactor`. Examples: `feature/6-live-upvotes`,
`chore/2-vercel-previews`.

### 3.3 Commits

Conventional Commits with the issue number as the scope:

```
<type>(#<issue>): <imperative summary, ≤ 72 chars>
```

Types: `test`, `feat`, `fix`, `refactor`, `chore`, `docs`, `ci`. Example: `test(#6): add failing tests for vote
ranking ties`.

### 3.4 TDD order (required — graded from git history)

1. `test(#n): …` — commit the new tests **while they fail**. Paste the failing `npm test` output into the PR.
2. `feat(#n): …` — the smallest implementation that makes them pass.
3. `refactor(#n): …` — clean up with tests green.

Never put tests and implementation in one commit. Never weaken or delete a test to make it pass.

### 3.5 Pull requests

- One PR per issue. Title = the main commit title. Body follows `.github/pull_request_template.md`.
- Required: CI green and **one approving review from the partner** (the author never self-merges). Reviewers
  leave at least one concrete comment (question, suggestion or confirmation of an AC), not a bare approval.
- Merge with **"Create a merge commit" or "Rebase and merge" — never "Squash and merge"** (squashing erases the
  failing-test commits).
- When an agent drafts review comments, each one cites `file:line` on the PR's **head commit**, and the human
  checks every line number and claim against the code before posting (drafts were off by a line on #19–#23).

## 4. Do

- Reuse before creating: `ok`, `errorResponse`, `ApiError`, `parseOrThrow`, `toErrorResponse`, design tokens,
  existing components.
- Put business rules in `src/lib/domain` and test them there first.
- Return DTOs from services (explicit `select`), never whole Prisma rows to the client.
- Format dates with `Intl` in the UI; keep ISO UTC strings in data.
- Pre-approved libraries (add in the PR that first needs them and name them): zod, jose, bcryptjs, Prisma,
  `lucide-react`, `@axe-core/playwright`, `qrcode`.
- Ask before adding any other dependency; name it and the reason in the PR.
- Add a new error code to `ErrorCode` in `http.ts` (with its status) instead of returning ad-hoc responses
  (`RATE_LIMITED` → 429 is added in #5).

## 5. Don't

- Don't use `next-auth`/Auth.js, Express, Socket.IO, Pusher, `axios`, `moment`/`dayjs`, `lodash`, Redux, CSS-in-JS or
  Jest.
- Don't call `db` from components, pages, route handlers or Server Actions — go through a service.
- Don't call `new Date()`, `Date.now()` or `Math.random()` inside `src/lib/domain`.
- Don't send hidden questions, merged questions or anonymous authors' names to guests or the public API.
- Don't use raw hex colors, inline `style` for theming, or `dangerouslySetInnerHTML` (question text is user input).
- Don't use `$queryRawUnsafe`/`$executeRawUnsafe`; use the Prisma query API.
- Don't add `.skip`/`.only`, disable lint rules, or lower coverage thresholds to get CI green.
- Don't silence a Semgrep finding without `// nosemgrep: <rule-id>` and the reason on the line above (#46).
- Don't edit `src/generated/**` or migrations that are already on `main`.
- Don't commit `.env`, secrets, API keys or tokens; never log passwords, JWTs or raw API keys.
- Don't write source files with Windows PowerShell `Set-Content`/`Out-File`: they add a BOM or replace non-ASCII
  characters (`§`, `–`) with `?`. Files are UTF-8 without BOM, LF line endings (`.gitattributes`).

## 6. Security and accessibility requirements

### 6.1 Security

- **JWT:** `jose` HS256, secret `JWT_SECRET` (≥ 32 chars, validated on first use by `getJwtSecret()`). Cookies `hu_session` and
  `hu_guest`: `httpOnly`, `secure` in production, `sameSite: "lax"`, `path: "/"`. Claims per PRD §3.
- **Passwords:** `bcryptjs` cost 12. Login failure message is always "Email or password is incorrect."
- **Authorization:** every mutating service checks the role for *that session*. A guest token from session A is
  rejected in session B (403). No token → 401.
- **API keys:** store only SHA-256 hash + prefix; compare hashes; other owners' sessions → 404.
- **Abuse:** question rate limit from PRD §4.2; React escapes text — never render user input as HTML.
- **Output:** never return `passwordHash`, emails of other users, or raw keys. Unknown errors → generic 500.
- **Randomness:** anything that grants access (join codes, API keys, tokens) comes from `node:crypto`, never
  `Math.random` (#43).
- **Redirects:** after login, only same-site paths through `safeNext()`; it rejects `//`, `\` and control
  characters, which browsers turn into another site (#40).
- **Output outside React:** user text written into Markdown, e-mail or HTML strings is escaped by us; React only
  escapes what it renders.
- **Third-party assets:** a CDN `<script>` or `<link>` is pinned to an exact version **and** has an `integrity` hash.
- **Supply chain:** `npm audit --audit-level=high`, gitleaks and Semgrep (#46) must pass on every PR. CodeQL and
  dependency review run only while the repo is public.

### 6.2 Accessibility (WCAG 2.1 AA)

- Semantic HTML: `<button>` for actions, `<Link>` for navigation, one `<h1>` per page, landmarks.
- Every input has a visible `<label>`; errors are linked with `aria-describedby`.
- Visible focus ring (`focus-visible:outline-2 outline-brand-600`); everything works by keyboard.
- Status never by color alone; use only the token pairs listed in `docs/ui-spec.md` §1 for small text.
- Live regions (`aria-live="polite"`) for vote counts, new-question notices and poll results.
- Tap targets ≥ 44 × 44 px; respect `prefers-reduced-motion` when cards re-order.
